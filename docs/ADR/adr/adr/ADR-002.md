

## ADR-002
- Status: In Review
- Date: TBD
- Decision: Tags and groups live in Stacknote's own database. Moving or renaming files always goes through a reviewable plan with an undo journal.

### Context
- Organization reuses the existing pipeline: note embeddings for clustering, the local LLM for naming tags and groups.
- Moving files can break links between notes (relative links, wiki links) and confuse sync tools such as Git, Syncthing or iCloud.
- Writing tags into files modifies user content and can cause sync conflicts.

## Decisions
| Area                | Choice                                                                                         |
|---------------------|------------------------------------------------------------------------------------------------|
| Tag storage         | SQLite (rusqlite) by default; writing tags to YAML front matter is opt-in                      |
| Grouping            | Cluster note-level embeddings (mean of chunk vectors) with k-means or HDBSCAN (linfa, hdbscan) |
| Group naming        | Local LLM names each group                                                                     |
| File reorganization | Plan → preview → apply, with per-item approval                                                 |
| Safety              | Undo journal for every applied plan; no deletes ever                                           |
| Links               | Rewrite relative markdown links and wiki links when files move                                 |

## Alternate Considerations

| Option                                  | Pros                                                     |
|-----------------------------------------|----------------------------------------------------------|
| Auto-move files without review          | Fastest; zero clicks for the user                        |
| Write tags into files by default        | Tags are portable to other apps (e.g. Obsidian)          |
| Suggest-only, no file moves at all      | No risk to the user's files                              |
| Plan → preview → apply with undo        | User stays in control; any reorganization can be undone  |

### Consequences

#### Positive
- Users stay in control of their files
- Any reorganization can be undone
- No sync conflicts from Stacknote writing into notes by default

#### Negative
- Extra preview UI and undo journal to build
- Link rewriting must handle several link styles
